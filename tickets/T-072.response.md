## 1. sim/enemy_arbiter.gd — the declarative gate

A pure sim object (RefCounted, floats and sqrt only, no engine call) that /no content id
appears anywhere in/test_boundaries.gd scans sim/ on every gate run.

Each enemy.json may set, in plain data (the cfg `arbiter` block) — two lists, ids
supplied by DATA, never named in code:
  "appear_requires": [ {"no_enemy_body_within": 12.0}, {"no_targeted_telegraph": true},
                       {"player_grounded": true}, {"not_on_glitched_floor": true} ]
      Requirement entries, ALL ANDed; an appearance may start only on a tick when every
      entry it lists holds on the live sim state. Empty/absent list = no gate.
  "yields_to": ["<another row's id>", ...]
      The gates named by that list outrank this one: while any of them holds a live
      countdown, the caller defers THIS row — its own timer is UNAFFECTED (SR-4 defers
      theStrike, the countdown keeps ticking, the call lands on the first free tick
      that follows).

Requirement vocabulary (fixed in the arbiter, evaluated against sim state):
  no_enemy_body_within  — <u>, 3D feet-to-feet distance against the world's live body list
  no_targeted_telegraph — no live telegraph footprint (circle/ring/box — the same cfg
                          shape api.telegraph already carries) covers the player's feet
  player_grounded       — the controller's grounded flag
  not_on_glitched_floor — the controller's current tile key vs the world's glitched map
An unknown vocabulary entry is always false — a spelling error reads as a blocked gate,
never as a silent yes. Footprints carry an optional y band, applied only when the shape
carries one. Distance form is 3D (D-T072-1, CONTESTABLE).

Deferral countdowns: the runtime's live telegraph list (an entry stays listed while its
ticks > 0), plus the optional caller-side `pending` ids a behavior keeps on its own row.

## 2. sim/controller.gd — the per-class lock, from data

`ctl.lock_abilities(whole ticks)`: the window runs for ticks/60 s; the per-class effect
list comes from data/player.json `ability_lock.lock_effect`:
  dasher   — dash_disabled: the dash cannot START (step gated the way it always was) and
             its cooldown does not tick while lock > 0 (the regen branch);
  glider   — glide_disabled: an ACTIVE glide ends the moment the call lands;
  athletic — class_multipliers_off: nothing to do inside the call — run_speed() and the
             air-jump height read ability_locked() every tick, so the x1.5/x1.3 class
             multipliers are already off while the window holds; purchased upgrades still
             work at normal strength, and the floor's own x0.8 slow sits on top.
Missing/empty data falls back to LOCK_EFFECT_FALLBACK (the full SR-6 reading), so a lock
can never be a silent no-op. api.lock_abilities routes through the new entry; no caller
changed.

The SR-6 numbers the tests assert: Athletic 10.35 -> 9.0 u/s when locked, 8.28 -> 7.2 on
the glitched floor (9 x 0.8 — the same floor speed as the other two classes), a +0.10
speed upgrade counting x1.0 while locked (11.70 -> 9.90).
