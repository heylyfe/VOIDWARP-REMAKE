# Cycle 4 adversarial review

Reviewed main at 4d14c5c in the actual main checkout.

## Confirmed defects

1. **Major — gift pickup radius is missing from the deterministic state hash.**
   `game/sim/gifts.gd:74`, `:83`, `:136`, `:241`; `game/sim/state_hash.gd:89`.
   Item 6 changes the base radius from a constant to data, but the GIFTS dump
   contains only phase and taken bits. Two identical generated level-1 states
   with base radii 0.4 and 0.7 both hash to
   `6ff9a7c60b6c4d900e95441924c36f746d3f058962a51d811407274b105ecfca`
   (independent `game/out/c4_radius_probe.gd`). The same input at a distance
   between those radii collects in only one state. Differing economy data can
   thus go undetected until the simulations diverge; the effective multiplier
   is also absent. This is the same class of missing configuration as the
   previously fixed collapse hash collision.

2. **Major — carried votes are not connected to the actual app's hash state.**
   `game/app/world.gd:311`, `:315`, `:355`;
   `game/sim/run_state.gd:40`; `game/tools/bot_run.gd:547`.
   The app keeps votes in `_ledger` and directly constructs a LevelState; it
   never creates/populates the RunState whose votes the hasher reads. Repository
   search finds the only production assignment in the standalone bot. Thus the
   new serialization proves a bot/constructed RunState, not a hash of the
   actual app run. There is no app-world replay/hash path here to validate.
   The replay test at `game/tests/test_enemy_stacking.gd:329` caps playback at
   600 ticks with max level 1, so it cannot demonstrate replay across a later
   lobby or reproduce a repeated carried vote. The separate eight-level carry
   test does check the app's ledger and spawning, but does not replay it.

3. **Major — the 0/90 figure does not establish zero unwinnable levels.**
   `tickets/B10.response.md:84`. The documented WIN calculation uses straight
   XZ distance and a 9 u/s speed, and STRAND uses the nearest later-falling tile.
   Neither checks a traversable route, height, gaps, jump timing, hazards, or
   a complete path from that tile to the beacon before subsequent falls.
   Consequently neither figure proves winnability. The same report at line 123
   gives 97/100 as a bot result, but `game/tools/bot_run.gd:535-705` directly
   steps controller, gifts, mines, beacon and enemies; it never constructs or
   ticks collapse. The report itself admits this at line 127: the number
   cannot be evidence of collapse survival. This finding concerns the evidence,
   not a demonstrated unwinnable generated level.

## Checks that held up

- Independent delay probe: 0, 19 and 20 seconds serialized trailing ticks
  0, 1140 and 1200 and produced three distinct SHA-256 hashes. The carried
  vote serializer sorts IDs and includes positive counts; changing constructed
  RunState vote counts changes the hash. The level-1 bot replay passed, within
  the narrower scope above.
- Searched all pickup-radius consumers: the new data value is read by gifts;
  the stat multiplier flows to gifts. Body dimensions, kill plane, mine contact
  and beacon constants remain separate. The added tests check these constants.
- Compared every changed test file for items 6, 9 and 10 with the pre-item-9 main, including
  every change in stats consumers and collapse. The removed collapse assertions
  were moved to the new crack-relative boundaries or updated to the new data;
  old zero-delay behavior has a separate test. Stats consumer expectations and
  its probe point were rescaled for the intended new base, retaining base,
  absent-stat, three stacks, curse, clamp, reset and pickup checks. No skipped
  assertion or unrelated weakening found. The shot script only shifts its
  reference tick. New files were examined for replay scope above.
- Targeted tests via `godot_console.exe` and `res://out/one.gd`:
  enemy stacking, platform collapse, gifts, stats consumers all reported
  `failures=0`. Gifts also emitted a dummy-renderer null-material error;
  stacking emitted exit-time object/RID leak warnings. Console executable was
  required because the GUI executable detached without returning output.
