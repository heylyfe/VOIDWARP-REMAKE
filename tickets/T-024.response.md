  named constant (`MIN_DISPLAY_SECONDS := 5.0`, DESIGN.md §2 [CANON] row). All logic is driven by an
  injected `advance(delta)` step; tests never sleep real time. A fast load completes on the first
  step at/after 5.0 s; a load slower than 5.0 s completes at its own duration with the real fraction
  on the bar (`set_load_progress(p)` lets the real loader report; the first report permanently wins
  over the simulated estimate). Tips load from `data/tips.json` (unchanged, 18 tips, 11 hazard_tell);
  the draw pool expands each hazard_tell tip ×3 (`HAZARD_TELL_WEIGHT := 3`), the rotation is a seeded

## Honest gaps / notes

1. **The 8 s ceiling.** DESIGN.md §2's "≤ 8 s total at level 30" is a target no document turns into a
   test; test_loading.gd only proves the ≥ 5.0 s floor and the 7 s simulated case from the ticket.
   Nobody has driven the real asset/level load yet (no boot scene), so the ceiling is unverified.
2. **Fast-hold completion point.** With a 0.05 s step clock, a fast load completes at the first step
   at/after 5.0 s (≈5.05 s in the test), i.e. "exactly ≥ 5.0 s" is asserted with one step of slack.
   Real frames will land within one frame of 5.0 s.
3. **`loading_finished` / `play_requested` have no consumers yet** — by design (no entry point in
   this wave). When the boot scene lands, the loading screen must call `set_load_progress()` from
   the real loader or the sim falls back to the 0.0-progress default and never completes.
4. **Memory/leak warnings** ("14 ObjectDB instances were leaked at exit", "1 resources still in use")
   are pre-existing engine-exit noise seen on the baseline run too, not from this ticket's tests.
