## How honest are these numbers (FINDINGS - read before trusting)

1. **Headless frame numbers cannot measure rendering.** No window, dummy renderer, no GPU
   submission - the p99 row is the CPU-side frame cost only. The sim-tick row is a valid
   CPU measurement. This is stated in the tool's own output (NOTE lines + the row's
   parenthesis) and in D-T061-5. No number is reported as if it measured a rendered frame.
2. **Even THIS machine's windowed run has an asterisk (D-T061-7).** The session desktop
   runs through a a virtual display adapter; the engine logs
   `Couldn't get Vulkan surface capabilities (VkResult error -13)` every frame - the
   swapchain never surfaces. The windowed p99 therefore still does not include a real
   presented frame; it is sim + camera + 22 billboards + engine overhead with a broken
   present path. The honest reading of A13 needs the owner's machine with a real display.
   `mean_sim_tick` (0.73 ms against a 2.0 ms bound) is solid either way.
3. **The death->run-over and gate->level rows are component-level** because the app
   orchestrator that owns the real transitions does not exist yet
   (`game/app/menu.gd`: "no boot scene exists yet"). Which rows I had to define: NONE -
   A12's five rows are fully specified in DESIGN.md section 2. What I had to define is the
   measurement method per row (D-T061-2, [CONTESTABLE]): each row measures against the
   real shipped code path that exists today (the loading screen component driven by the
   measured build; the build pipeline as the gate->level cost; the kill-to-screen chain at
   sim + screen_data + run_over build; the controller's own fall->respawn window). When
   the app flow lands, rows 1-4 must be re-measured with the real transitions.

## What the pinned scene exposed and what I did about it

- **The 22-enemy vote list could not place through `plan()`.** Three defects in
  `sim/enemy_runtime.gd`'s retry path (D-T061-6): a deferral `return`-ed and silently
  DROPPED every planned entry behind it; a partially-spawned entry was re-appended WHOLE,
  duplicating its already-placed copies (observed: coil x6 from a x2 plan); and the SR-3
  30 u separation was enforced against the WHOLE roster instead of "copies of one chaser"
  (SR-3's own sentence; `_pick_round_trip`'s comment agrees), which starved a dense vote
  list permanently - every retry re-scanning the whole movement graph. Fixed all three;
  all 22 enemies now place exactly per the pinned vote list (the probe asserts 22 rows
  live and FAILs otherwise). Regression pinned in `game/tests/test_spawn_rule.gd`
  (`_deferral_keeps_the_plan`). This touched another ticket's module - the fix follows
  the documents, never weakens a check; flag for the T-027/T-056 owners.
- **`view/billboard.gd` crashed on a documented schema value**: the T-016 schema stores
  `world_height: null` where the design gives an enemy no body row (the nuke launcher);
  `float(null)` errored on every windowed run. Null now reads 0.0 (no body).
- The perf probe pins `spawn_delay_ticks = 1` (probe opts only) so all 22 bodies are live
  for every measured frame; the game's 6.0 s spawn rule (D-056) is untouched.
